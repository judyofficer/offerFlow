## 开发踩坑与 Bug 修复记录
- **问题现象**：执行 `npm run dev` 后，首页出现白屏，无法正常渲染。
- **排查过程**：执行 `npm run build` 时发现多处 TypeScript 编译报错，错误码为 `TS1484` 和 `TS6133`。
- **根本原因**：Vite 的 React TS 模板默认开启了 `verbatimModuleSyntax` 选项。这要求在导入纯 TypeScript 类型 (Type/Interface) 时，必须显式地使用 `import type` 语法。如果把类型和普通的变量混在同一个普通 `import` 里面（或者对类型使用普通 import），TypeScript 编译器就会抛出 `TS1484` 错误，从而导致 Vite 编译失败并阻断渲染。
- **解决方案**：遍历了 `App.tsx` 以及 Zustand store 和各个 page 文件，将类似于 `import { ApplicationStatus } from ...` 的类型导入全部修改为 `import type { ApplicationStatus } from ...`。修复后项目编译顺利通过，白屏问题解决。

### 3. 【开发遇到的问题 & 踩坑记录】
在本轮打磨中，遇到了几个极为隐蔽但又极其经典的“深水坑”：
1. **拖拽白屏导致 React Invariant 崩溃 (元凶：LLM 编造假 ID)**
   - **坑点**：拖拽简历编辑器中的某个区块时，突然整个页面白屏崩溃。
   - **排查**：控制台报错指出 `@hello-pangea/dnd` 找不到对应的 draggableId。追踪发现，因为提示词里让 LLM 返回 `id: "随机短字符串"`，大模型竟直接把所有的 `id` 都填成了字面量 `"随机短字符串"`！这导致 React 渲染时 `key` 冲突，拖拽库在底层绑定 DOM 时直接乱套，引发 Invariant 异常并导致整个 React 组件树崩溃。
   - **解法**：在 `resumeParser.ts` 接收到 JSON 后，拦截并主动使用 `Math.random()` 覆写所有数据项的 ID，确保绝对唯一。
2. **拖拽局部留出双倍空白位置 (元凶：样式优先级覆盖)**
   - **坑点**：拖拽组件时不再白屏崩溃，但拖拽的卡片下方空出了两倍的留白，不仅不丝滑，还严重破坏了排版。
   - **排查**：检查代码发现 `<div style={{ ...provided.draggableProps.style, position: 'relative' }}>` 的写法中，我们硬编码的 `position: 'relative'` 覆写了拖拽库动态计算赋值的 `position: fixed`（拖拽库在拖动时需要脱离文档流）。由于元素没有脱离文档流，再加上拖拽库原本插入的 Placeholder（占位符），两者叠加就霸占了双倍的高度。
   - **解法**：严格遵循 dnd 库的最佳实践，将扩展符写在样式对象的最后 `style={{ position: 'relative', ..., ...provided.draggableProps.style }}`，保障拖拽库的动态计算样式拥有最高优先级。
3. **CSS Animation Keyframes 遗漏**
   - **坑点**：在增加解析遮罩层时使用了 `animation: spin 2s linear infinite`，但是 `Loader` 图标并没有转动。
   - **解法**：发现是因为在 `index.css` 忘记全局注册 `@keyframes spin` 导致的，补全后即刻恢复旋转。

### 5. 【性能优化：防抖自动保存机制】
- **问题现象**：原有的 Zustand `persist` 默认是同步的。用户在简历编辑器中每敲击一个字符，都会触发一整棵简历状态树的深度 JSON 序列化并阻塞式地写入 `localStorage`，导致严重的输入卡顿。
- **解决方案**：引入了 `createDebouncedStorage` 工具函数，拦截并接管了 Zustand 的 `setItem` 操作，将其改为基于 1000ms 延迟的防抖（Debounce）写入。
- **数据安全保障**：为了避免防抖延迟期间用户突然关闭标签页导致数据丢失，在 `createDebouncedStorage` 内部绑定了 `beforeunload` 和 `visibilitychange` 原生事件。当检测到页面即将卸载或切换至后台时，会瞬间触发 `flush()`，同步将内存中 pending 的最新数据刷入 `localStorage`，实现了“高性能输入 + 零数据丢失”的最佳平衡。

### 6. 【功能迭代：全局撤销重做 (Ctrl+Z)】
- **问题现象**：简历编辑过程中（尤其是拖拽重排和模块增删），用户极易发生误操作。缺乏全局撤销会导致破坏性数据丢失，严重影响产品可用性。
- **架构决策 (ADR-006)**：我们拒绝了复杂的 Command 模式，选择了 **Memento Pattern (备忘录/快照模式)**，在 `useResumeStore` 中纯手写维护了 `past` 和 `future` 栈，保障了状态恢复的绝对可靠性。
- **技术亮点**：
  - **动态防抖入栈**：针对高频打字，不是每敲一个字母就记录一次快照，而是采用 `1000ms` 防抖拦截，实现了类似 Word 的“段落级”撤销。
  - **原生冲突规避**：在全局绑定 `Ctrl+Z` / `Cmd+Z` 时，智能判断当前焦点是否在 `INPUT` 或 `TEXTAREA` 内。如果在，则放行原生事件（触发浏览器默认文本撤销）；只有在外部时，才触发应用的模块级状态回滚。

### 4. 【关键决策理由】
- **为什么放弃复杂的手动保存，选择防抖自动保存？** 现代 Web 应用（如 Notion、Figma）已经确立了“所见即所存”的用户心智。增加一个“保存”按钮属于逆时代潮流。通过防抖机制控制写入频率，在体验上做到了无感知，在性能上解决了 I/O 阻塞。
- **为什么预览功能要自己弹 Modal 内嵌 iframe？** 因为直接下载源文件打断了用户体验（必须去系统的下载文件夹翻找，再用外部工具打开）。使用原生 iframe 的 `#view=FitH` 参数不仅能极速渲染，还可以让用户留在应用内部，并直接享受浏览器级 PDF 查看器的全部特性（包括另存为、打印等）。
- **为什么不让 LLM 返回真实随机 ID 而是靠前端兜底？** 经过测试，不管怎么在 prompt 里强调，各类大模型在生成纯结构化数据的字段校验时极不稳定，有的返回 1，有的返回 literal string。前端兜底生成 ID 成本极低（一行 `forEach`），且 100% 杜绝了系统级崩溃，是投入产出比最高的工程决策。

### 8. 【工程部署：Vercel 生产环境配置】
- **部署环境**：Vercel
- **问题与挑战**：由于我们使用的是纯前端的 React Router (`BrowserRouter`)，一旦将代码推送到 Vercel 等静态托管平台，如果在非根目录 `/` 刷新页面，Vercel 默认会去查找对应的静态目录文件，导致报出 404 Not Found 错误。

- **Mock数据策略**：最终决定保留 `mockDataInjector` 的自动注入演示数据，让初次访问的用户立刻看到丰富的数据效果，增强开源作品集的展示能力。

### 9. 【工程部署：Netlify 生产环境配置】
- **问题与挑战**：切换到 Netlify 部署后，由于使用了 React Router (`BrowserRouter`)，子路由（如 `/jobs`）在刷新时直接报出 404 Page Not Found，这是因为 Netlify 默认找不到对应的静态 HTML 文件。
- **解决方案**：在 `public/` 目录下新增了 `_redirects` 配置文件，加入规则 `/* /index.html 200`。Vite 打包时会自动将此文件后台合并，完美解决了 SPA 的 404 问题。

- **关键决策理由**：
  - 优秀的前端简历排版工具（如 Reactive Resume）核心价值就在于“边距与密度的可控性”。提供「一键自适应单页」结合「参数微调面板」，兼顾了小白用户的“一键搞定”诉求与极客用户的“像素级微调”诉求。

### 3. 【开发遇到的问题 & 踩坑记录】

1. **React Hook 条件调用报错（`react-hooks/rules-of-hooks`）**:
   - **现象**：构建与 Lint 时报错 `React Hook "useResumeStore" is called conditionally. React Hooks must be called in the exact same order in every component render`。

2. **A4 物理纸张（794px）在手机端（390px）的缩放与占位塌陷问题**:
   - **现象**：使用 CSS `transform: scale(...)` 缩小 A4 画布时，默认原点在中心（导致左右偏移），且 `transform` 不会改变元素在父容器中的几何占位（Bounding Box），导致外层滚动容器仍留有 794px 的空白或产生水平滚动条。
   - **解决方案**：采用双层嵌套容器架构：
     - 外层容器：宽度设定为真实的视口缩放宽度 `Math.round(794 * effectiveZoom)px`，居中对齐。
     - 内层容器：固定为物理 A4 宽度 `794px`，设置 `transform: scale(...)` 并将变形原点锁定在左上角 `transformOrigin: top left`。
     - 效果：在 390px 屏幕下刚好缩放至约 365px，整个 A4 简历完整自适应呈现，零水平位移，零横向滚动条，犹如在手机上看原生 PDF 预览。

#### 从“伪 HTML 表格布局”向“Word 原生排版流引擎”的重构

```
【旧版崩溃根源（伪表格流）】
Section Banner ──> Table (WidthType.PERCENTAGE: 100 -> 实际被 Word 识别为 2% 宽度并带虚线网格)
TwoColumn Item ──> Table (WidthType.PERCENTAGE: 72 -> 实际被 Word 识别为 1.4% 宽度，文字单字垂直断行)
Header         ──> Table (WidthType.PERCENTAGE: 82 -> 姓名和联系方式被压缩成细长右侧长条)

【新版 Word 原生排版流引擎】
┌─────────────────────────────────────────────────────────────┐
│ 1. Header: 原生文本流或绝对 DXA 列宽双列容器 (左侧占满 85%+) │
│ 2. Banner: 原生 Paragraph (shading: F2F4F7, border-left: 1F2937) 全宽无缝 │
│ 3. TwoColumn: [名称 (加粗)] + Tab() + [时间 (右对齐制表位)]   │
│ 4. Details: Markdown 语法解析 + 原生 bullet 列表流           │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
在 Microsoft Word / WPS 中打开：
• 0 虚线表格框（无任何 Table Gridlines 残留）
• 文字横向舒展自然，不再被挤到右侧
• 排版完全 1:1 还原 OfferFlow 网页高保真预览
```

---

### 3. 【开发遇到的问题 & 踩坑记录】
1. **OpenXML 中百分比宽度单位规范的陷阱**：
   - **问题**：在 CSS 中 `width: 100%` 表示 100%；但在 Office OpenXML（ISO/IEC 29500）规范中，`w:tblW w:type="pct"` 的基数是 `5000`（即 5000 代表 100%，50 代表 1%）。传入 `100` 会被 Word 识别为 `2%`，传入 `72` 会被识别为 `1.4%`。
   - **解决方案**：在 Word 文档生成中，尽量避免使用百分比 Table。对于版面对齐，优先采用 Word 原生的制表位（`TabStop`）；如必须使用 Table（如头像与文字），必须使用确定的绝对像素单位（`WidthType.DXA`），彻底规避单位解析歧义。
2. **Word 查看网格线（View Gridlines）造成的视觉污染**：
   - **问题**：即使在 CSS 中设置 `border: none`，Word 在默认开启“表格网格线”视图时，依然会在所有无边框表格周围画出一圈浅灰色的虚线框，严重影响简历的美感。
   - **解决方案**：将原本用于两极对齐的表格全部替换为段落制表位（TabStop），从根源上移除 DOM 中的表格结构，彻底消除虚线网格。

---

### 4. 【关键决策理由】
- **为什么坚决摒弃表格、全面转向制表位（TabStop）？**
  - 在文字排版领域，表格是为结构化数据矩阵（如统计表、财务报表）设计的，而非用于常规文本的左右对齐。用表格做版面布局不仅会引入网格线干扰和宽度计算风险，还会导致用户在 Word 中选中文字、换行或微调时遇到跨单元格的割裂感。采用制表位对齐是 Word 官方标准规范，兼顾了排版的稳固性与用户二次打字编辑的丝滑体验。

### 3. 【开发遇到的问题 & 踩坑记录】

1. **直接受控输入框打字导致的光标跳动与删除截断问题**：
   - **问题**：若将 `<input type="number">` 直接受控绑定外部传入的 `value` 并在 `onChange` 中立即转换为 `parseInt/parseFloat`：
     当用户想把 `24` 改为 `26` 时，按 Backspace 删掉 `4` 留下 `2`，若触发 `Math.max(12, 2)`，输入框会被立即弹回 `12`，导致用户无法正常键入多位数字；若将内容全删空，`parseFloat("")` 为 `NaN`，若直接写入 store 会导致简历排版样式计算崩溃。
   - **解决方案**：在 `LayoutSliderControl` 中设立 `localText` 本地字符串缓冲。打字时允许保留临时非完整状态；只有在解析为合法数值且在合理区间时才即时通知 Store；用户按回车或离开焦点时才进行最终格式化与安全区间裁剪（Clamping），兼顾了实时响应与打字容错。

2. **跨浏览器数字输入框（Spinner）外观破坏统一设计质感**：
   - **问题**：原生数字输入框在 WebKit 与 Firefox 浏览器下会附带样式粗糙的上下箭头，占用横向宽度且无法与设计系统主题颜色协调。
   - **解决方案**：针对 Webkit 内核（`-webkit-appearance: none;`）与 Firefox（`-moz-appearance: textfield;`）彻底隐藏默认 spinner，将输入框置于自定义样式的胶囊包裹容器中，右侧拼接固定或按需显示的单位标识（如 `px`），呈现一致的高级质感。

### 4. 【关键决策理由】

1. **为什么选择“滑块 + 输入框并存”而非纯输入框或纯滑块？**

2. **为什么使用 React 19 `useDeferredValue` 而非手写 `setTimeout` 防抖？**

### 2. 【架构与设计变更】

#### Rollup 代码分割算法在处理 Dynamic Import Helper 时的“隐式反向依赖”陷阱

```
【原有缺陷拓扑（Helper 污染引发反向强引用）】
1. manualChunks 强行配置: id.includes('pdfjs-dist') => 'vendor-pdfjs'

1. 移除对纯动态业务库的 manualChunks 强行命名，pdfjs 仅在 extractTextFromPdf 内部动态 await import
2. __vitePreload 助手函数自然归属主入口/运行时核心 runtime chunk
```

### 3. 【开发遇到的问题 & 踩坑记录】
1. **动态 `import()` 为什么还是在 DevTools 网络面板首屏出现？**
   - **问题现象**：明明在组件中写了 `await import('../../services/resumeParser')`，但在生产部署的 Chrome DevTools 网络瀑布中，`vendor-pdfjs` 依然赫然出现在首屏的前几个请求中，启动器显示 `(索引):19`。
   - **深入排查过程**：
     - ① 检查 `dist/index.html`，发现第 19 行确实存在 `<link rel="modulepreload" href="/assets/vendor-pdfjs.js">`；
     - ② 逆向分析打包后的 `dist/assets/index.js`，发现它开头第一行写着 `import { i as u } from "./vendor-pdfjs.js"`；
     - ③ 继续溯源符号 `u`，发现它并不是 pdfjs 的任何业务逻辑，而是 Vite 用于处理 `React.lazy` 的动态导入预加载工具函数 `__vitePreload`；

     - 取消对非首屏高频共用库的 `manualChunks` 强行提权，保持其纯粹的动态异步叶子属性；
     - 配合模块内的延迟 `await import('pdfjs-dist')`，彻底斩断辅助代码的交叉污染。

### 4. 【关键决策理由】
- **哪些包适合放 `manualChunks`？哪些包绝对不应放 `manualChunks`？**
  - **适合放 `manualChunks` 的包**：首屏高频使用且极少变动的“基础设施级基础库”（如 `react`、`react-dom`、`react-router-dom`、`zustand`）。把它们单独提取能极大提升浏览器对这些静态资源的持久化缓存命中率；
  - **绝对不应在 `manualChunks` 中强行抽取的包**：只在某个特定的、低频的子页面或异步操作中使用的第三方重型工具库（如 `pdfjs-dist`、`@hello-pangea/dnd`、`docx`）。这类库应完全交给打包器按照异步加载链路自然形成独立的动态 Chunk，否则极易诱发公共 Helper 跨层污染，让按需加载沦为形式主义。

### 3. 【开发遇到的问题 & 踩坑记录】
1. **连续文本片段分别加粗导致的碎标记问题（`**React**** 19**`）**：
   - **问题**：在 PDF 字形流中，“React”和“19”可能是两个相邻的 textItem 且都是粗体。如果对每个 item 简单加 `**${item.str}**`，会导致生成 `**React**** 19**` 碎片。
   - **解决方案**：引入布尔状态机 `inBold`。只有在字体由非粗体变为粗体时才开启 `**`，在由粗体变为非粗体或换行时才闭合 `**`，生成连续优雅的 `**React 19**`。
2. **前后空格包裹导致的 CommonMark 渲染失效**：
   - **问题**：若加粗文本前后包含空格（如 `** React **`），标准 Markdown 解析器可能无法识别加粗。
   - **解决方案**：在开启和闭合加粗时，自动提取并保留首尾空白字符，输出规范的 ` **React** `。

### 4. 【关键决策理由】
- **为什么必须从底层 PDF 提取加粗，而不是让 AI 自动加粗？**
  - 求职简历的排版是一门精细的艺术，求职者对哪些项目、哪些数字、哪些技术栈加粗，蕴含了其个人的表达策略与求职重心。AI 的主观猜测往往会造成“加粗泛滥”或“错位强调”，破坏了用户的原版意图。通过底层 PDF 物理字形属性精准提取，实现了真正的“所见即所解、原样高保真”。

### 3. 【开发遇到的问题 & 踩坑记录】

1. **批量打开新标签页（Batch Window Open）被浏览器拦截（Popup Blocker）**：
   - **问题现象**：在 Web 环境下，如果在单个点击事件中无限制循环 `window.open` 10~20 个网页，浏览器（Chrome / Safari）会自动将其判定为恶意弹窗并拦截。
   - **解决方案**：设计“批量打开前 5 个”的阈值限制，并在直通车界面上明确给出提示；同时为每个岗位保留独立的“今日已查”单点击穿透，用户可逐个点击，点击后按钮自动变为“今日已查（绿色打钩）”，状态清晰明了。
2. **看板卡片点击事件冒泡（Event Bubbling）冲突**：
   - **问题现象**：点击卡片底部的“查进度”按钮时，不仅会打开新网页，还会同时触发卡片外层的 `onClick` 打开右侧详情抽屉，造成视觉干扰。
   - **解决方案**：在卡片和表格的直达按钮 `onClick` 处理器上统一调用 `e.stopPropagation()`，保证只触发网页跳转而不弹出抽屉面板。

### 4. 【关键决策理由】

- **为什么不仅做单点直达，还要专门设计【进度直通车 (Progress Hub)】？**
  - **海投高频痛点剖析**：当求职者投递了 30~50+ 家公司后，每天早上最重要的事情是“巡检各家公司的进度”。如果用户需要在看板或表格里一个一个翻找、滚动屏幕、点击卡片，依然存在巨大的操作负担。进度直通车提供了一个专注的“晨检/巡检模式”，只罗列当前处于进行中的岗位，一键批量或逐个点亮查验，并支持在同一界面直接把状态从“已投递”推到“笔试/面试中”，将原本 5 分钟的繁琐操作压缩到 30 秒以内。
- **为什么内置名企招聘官网字典库？**
  - 许多求职者在从招聘群或牛客网看到招聘信息时，手头可能没有留存具体的投递后台网址。内置大厂官方入口字典库，即便用户只填了“字节跳动”或“腾讯”，系统也能瞬间精准直达其应聘记录中心，极大提升了产品的“懂求职者”的智能化体验。

### 3. 【开发遇到的问题 & 踩坑记录】

1. **`border: 1px` 与 `border: 2px` 在 `border-box` 模式下的物理高度差**:

### 3. 【开发遇到的问题 & 踩坑记录】

1. **跨月份与跨天日期的毫秒差取整问题**:
   - **现象**：直接使用 `(Date2 - Date1) / 86400000` 在跨夏令时或不同时间点可能产生 `2.95` 等浮点数，导致天数计算偏差 1 天。
   - **解决方案**：统一通过 `split('-').map(Number)` 提取年月日并调用 `setHours(0, 0, 0, 0)` 抹平时间差，再使用 `Math.round` 精确计算跨越自然日天数。
2. **日历月视图多条目超出 112px 单元格高度的问题**:
   - **现象**：当同一天既有 2 个面试，又叠加了 2 个跨天进行中时限时，单元格高度容易被撑大或文字重叠。
   - **解决方案**：在渲染层建立优先级调度机制（Direct 未完成 > Ongoing 时限 > Completed 已完成），超出 2 项时优雅折叠为 `+N 项更多` 徽章，既不丢信息又稳固 112px 严整网格。

### 4. 【关键决策理由】

1. **为什么截止前各天采用次级浅色虚线展示，而非等同于当天直接日程？**
   - 如果跨天时限在每天都用鲜艳高亮的卡片填满，会导致用户视觉疲劳，分不清“今天必须去参加的面试”和“未来几天内可选时间做的笔试”。次级虚线胶囊既起到“随眼可见、不会遗忘”的提醒效果，又保持了主次分明。
2. **为什么截止前将时限日程放入当天的日程安排，并在完成后移出？**
   - 绝大多数求职者习惯看“今日待办”。只要时限任务还没做，今天就是一个潜在的可作答窗口，理应出现在今日工作台；而一旦作答完毕打勾，它就完成了历史使命，移出今日待办能够提供极佳的掌控感与清空待办的愉悦感。

### 3. 【开发遇到的问题 & 踩坑记录】
1. **CSS Grid 与内联动态行高的冲突问题**：
   - **问题**：在桌面端需要根据当月周数（4~6周）动态计算 `gridTemplateRows: repeat(${weekCount}, minmax(78px, 94px))`，但内联样式优先级高于常规 CSS 类名，导致移动端 `@media` 中的 `48px` 被内联样式覆盖，日历单元格在移动端依然被拉长。
   - **解决方案**：在 JSX 中通过 CSS 变量绑定 `['--week-count' as any]: weekCount`，将动态行高逻辑迁移至 CSS 中，桌面端使用 `grid-template-rows: repeat(var(--week-count, 5), minmax(78px, 94px))`，移动端通过 `@media (max-width: 768px)` 优雅重载为 `repeat(var(--week-count, 5), 48px) !important`，实现 0 JS 布局抖动的纯 CSS 响应式控制。

### 4. 【关键决策理由】
1. **为什么在日历单元格上使用“纯 CSS 双轨切换”而不是“JS 动态判断屏幕宽度”？**
   - **高性能与 0 抖动**：使用 `@media` 可以在浏览器解析 CSS 时以 60fps 瞬间完成断点切换，避免因 `window.innerWidth` 监听引入的重渲染、ResizeObserver 抖动或 SSR 水合不一致问题。
2. **为什么移动端日历只展示圆点指示器，卡片放在下方？**
   - **符合移动端人体工学与触控交互最佳实践**：在 40px 的微型触摸格子里塞入按钮和长文本会导致误触和严重的视觉割裂；将“全月概览”和“当日详情操作”上下垂直分离，既保留了日历的大局观，又保证了操作区域有足够舒适的触控热区（如 44px 按钮），体验最符合移动端用户心智。
